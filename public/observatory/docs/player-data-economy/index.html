Player data and economy

PlayerDataManager owns the profile lifecycle. Economy and progression services mutate the loaded profile through that authority rather than keeping parallel save data.

Profile lifecycle​

Player joins
   |
   v
load ProfileService profile
   |
   v
reconcile DefaultData
   |
   +--> LocalData registry
   +--> replicated state
   +--> DataSync snapshot
   |
player leaves / shutdown
   |
   v
run release callbacks -> release profile -> clean state

The manager exposes full profile access only on the server. UserProfile on the client receives full and partial synchronization events and should be treated as a presentation cache, not an authority.

Saved schema​

The default profile contains:

RootData
SettingsGraphics, audio, caustics, notifications, head movement, debris, gear visibility, and tutorial state
StatisticsEvents, scans, exploration, playtime, currency, dives, trash, and minigames
CurrencyBalance, earned/spent totals, income timing, streaks, and source accounting
EcoPointsEnvironmental balance and source accounting
DiscoveriesPersisted discovery identifiers
AchievementsProgress, unlock, and claim state
OwnedItemsOwnership, equipped state, category, slot, and grant metadata
CollectedTreasuresDaily or reset-bound treasure state
TipjarDonation ledger and listing visibility
AnalyticsTrackingInterface tracking records

When adding a field, update DefaultData and decide whether existing profiles can be reconciled safely or need an explicit migration keyed by __version.

Replication​

DataSync carries initial state. DataPartialSync updates a scoped portion of the client cache. Currency and eco-point balances also expose named Mince state objects for responsive UI.

Do not send internal ProfileService objects or server-only bookkeeping to the client.

CurrencyService​

CurrencyService owns mutations for the primary currency and Eco Points. Its public operations include grant, spend, balance lookup, trash collection, passive income, scan rewards, event rewards, and exploration rewards.

Each transaction:

  1. resolves the active profile,
  2. validates amount and balance,
  3. updates totals and per-source accounting,
  4. synchronizes replicated state,
  5. reports economy analytics,
  6. sends a player-facing notification when appropriate.

Achievements and statistics​

AchievementService records stat progress, unlocks configured achievements, handles claims, and emits update/toast messages. Achievement definitions live in Runtime.Config.Shared.Achievements.

Statistics should be changed through their owning service so achievement progress and analytics remain consistent.

Safe mutation checklist​

  • Reject non-finite, negative, or unexpected amounts.
  • Resolve item prices from server configuration.
  • Keep receipt processing idempotent.
  • Update saved totals and current balance together.
  • Synchronize only after the mutation succeeds.
  • Register release callbacks for any service holding per-player state.
  • Test join, rejoin, forced save, leave, and shutdown paths.
