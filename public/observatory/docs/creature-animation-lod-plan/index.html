Creature Animation LOD Plan

This checklist breaks creature animation optimization into reversible phases. Complete and measure each phase before starting the next one.

Goals​

  • Reduce client animation, skinning, and simulation CPU cost.
  • Keep nearby creatures smooth and visually unchanged.
  • Reduce update frequency for medium-distance creatures.
  • Stop animation and simulation for distant creatures.
  • Avoid creating a Heartbeat, RenderStepped, or PreSimulation connection per creature or school.
  • Preserve creature events, scanning, discovery, and exhibit interactions.

Current Baseline​

Observed place totals:

  • Approximately 266 instances tagged Creatures.
  • Approximately 52 instances tagged Boid.
  • Approximately 323 AnimationController instances.
  • Approximately 3,116 bones and 4,705 mesh parts.

Relevant runtime paths:

  • ReplicatedStorage.Runtime.Source.Components.Creatures
  • ServerScriptService.Runtime.Source.Components.ServerCreatures
  • ReplicatedStorage.Runtime.Source.Components.FishComponent
  • ReplicatedStorage.Runtime.Source.Controllers.FishController
  • ReplicatedStorage.Modules.FishBrain
  • ReplicatedStorage.Modules.FishBehaviour

Known architectural issues:

  • The Creatures component immediately loads and plays every valid animation without distance or visibility checks.
  • ServerCreatures also loads and plays animations, so ownership must be audited to prevent duplicate server/client animation work.
  • Each fish school created by FishBrain owns a PreSimulation connection.
  • FishBehaviour also has a global PreSimulation path, but the group registration API is not consistently used by FishBrain.
  • Fish visual interpolation runs every rendered frame for all entries in VisualCFrameTargets.
  • Animation speed adjustments can traverse descendants when cached tracks are unavailable.
  • FishController already performs a 0.3-second octree distance query, making it the natural owner for activation state.

Initial values are intentionally conservative and should become configuration values after validation.

Phase 0 — Measurement and Safety Net​

  • Record client FPS with creature simulation enabled and disabled.
  • Capture MicroProfiler samples at the observatory, aquarium, and open-water areas.
  • Record Script Profiler time for Creatures, FishController, FishBrain, and FishBehaviour.
  • Count active animation tracks by LOD tier.
  • Count active fish, schools, and visual interpolation targets.
  • Record client memory and CPU from an empty server after 60 seconds.
  • Record the same values with at least one additional player.
  • Add a temporary developer-only metrics API or attributes for active/dormant counts.
  • Confirm scanning, discovery, animation markers, and creature events before changes.
  • Save baseline screenshots or video for visual comparison.

Exit criteria:

  • Baseline numbers are recorded in this document or a linked results document.
  • A repeatable playtest route exists.

Phase 1 — Static Creature Animation Manager​

Scope: instances tagged Creatures and ServerCreatures, excluding boid schools.

  • Create one client CreatureAnimationController responsible for animation activation decisions.
  • Register/unregister creature components with the controller.
  • Cache each creature's root part, animator, animation track, and event-marker connections once.
  • Replace unconditional AnimationTrack:Play() with controller-owned activation.
  • Evaluate creature distance from the camera or character on a shared 5 Hz scheduler task.
  • Keep near creature tracks playing normally.
  • Pause medium/far tracks without destroying and reloading them.
  • Stop dormant tracks after a grace period to prevent rapid boundary thrashing.
  • Add LOD hysteresis so a creature does not repeatedly start and stop near a boundary.
  • Disconnect marker events when a component is removed.
  • Remove debug prints from animation markers.
  • Audit ServerCreatures and document which animations genuinely require server ownership.
  • Remove duplicate server animation playback where animation is cosmetic-only.
  • Preserve server-owned animation only when gameplay or replicated marker behavior requires it.

Exit criteria:

  • Nearby static creature animation looks unchanged.
  • Distant static creature tracks stop consuming animation time.
  • No duplicate track is created when crossing an LOD boundary repeatedly.
  • Creature event emitters still fire exactly once when expected.

Rollback:

  • A configuration flag can restore unconditional animation playback.

Phase 2 — Fish School Activation Ownership​

Scope: FishComponent, FishController, and FishBrain lifecycle.

  • Make FishController the single owner of school activation and LOD selection.
  • Replace the hardcoded local DesiredDrawDistance = 200 or ... expression with a real player setting fallback.
  • Store tracked school positions in the octree and update nodes when regions move.
  • Assign each school an explicit Near, Medium, Far, or Dormant state.
  • Use separate enter/exit radii to prevent activation thrashing.
  • Remove one PreSimulation connection per FishBrain instance.
  • Register active fish groups with the existing global FishBehaviour.RegisterGroup path.
  • Unregister groups on stop and destruction.
  • Ensure dormant fish are not left in global interpolation or animation caches.
  • Avoid reparenting every fish repeatedly when crossing a boundary; compare pausing versus dormant storage.
  • Confirm stopped schools can resume without duplicating fish or animation tracks.

Exit criteria:

  • There is one shared fish simulation connection per client.
  • Dormant schools perform no simulation or interpolation work.
  • Repeated activation does not increase connections, fish count, or memory.

Rollback:

  • A feature flag can restore the existing FishBrain connection behavior.

Phase 3 — Simulation and Animation LOD​

Scope: active boids inside FishBehaviour.

  • Pass the school LOD tier into FishGroup:Step rather than calculating inconsistent tiers in multiple places.
  • Near schools simulate at approximately 30 Hz.
  • Medium schools simulate at 10–15 Hz.
  • Far schools simulate at 4–6 Hz with reduced neighbor counts.
  • Dormant schools do not call FishGroup:Step.
  • Limit obstacle raycasts by tier.
  • Limit leadership and school-center recalculation by tier.
  • Cache animation tracks for every fish; remove descendant scans from hot paths.
  • Adjust animation speed only when the delta exceeds the existing threshold.
  • Pause fish animation tracks in the dormant tier.
  • Resume tracks without calling LoadAnimation again.
  • Bound the global CFrame queue and carry excess work into the next frame.
  • Remove stale VisualCFrameTargets immediately when fish become dormant.
  • Interpolate only near and medium fish every rendered frame.
  • Use coarse direct transforms for far fish.

Exit criteria:

  • Frame time remains stable when entering an area with several schools.
  • Simulation work scales with nearby fish rather than total fish in the place.
  • No visible teleporting occurs at the near/medium boundary.
  • Far fish remain visually acceptable at the target camera distance.

Phase 4 — Adaptive Quality and Streaming​

  • Move LOD distances and update rates into shared configuration.
  • Define desktop, console, and mobile presets.
  • Base adaptive quality on a rolling frame-time average, not a single frame.
  • Degrade one tier at a time after sustained low FPS.
  • Recover quality slowly after sustained healthy FPS.
  • Respect the player's draw-distance setting.
  • Verify behavior with Workspace.StreamingEnabled on and off.
  • Handle streamed-out creatures as unregister events without warnings.
  • Avoid loading animation tracks until the creature is eligible for an active tier.
  • Add a maximum number of simultaneously animated skinned creatures per device preset.

Exit criteria:

  • Mobile and low-performance clients automatically reduce creature cost.
  • Quality recovery does not cause frame-time spikes.
  • Streaming in/out does not leak tracks, connections, or component state.

Phase 5 — Validation and Rollout​

  • Repeat the Phase 0 playtest route.
  • Compare CPU, FPS, frame time, memory, and active track counts against baseline.
  • Test all creature event-marker effects.
  • Test scanning and discovery on near, far, stopped, and resumed creatures.
  • Test player teleportation between areas to force rapid LOD changes.
  • Test two clients observing the same creatures from different distances.
  • Test Studio, desktop client, mobile emulation, and console emulation.
  • Run for at least 20 minutes and check for connection or memory growth.
  • Remove temporary diagnostic output.
  • Keep metrics accessible behind a developer flag.
  • Roll out behind a feature flag before making it the default.
  • Record final measurements and mark the selected default thresholds.

Success Criteria​

  • At least a 30% reduction in creature-related client script time in the heavy test area.
  • No more than 10% of total creature tracks active while the player is far from exhibits and schools.
  • No per-creature or per-school frame connection for activation decisions.
  • Stable connection and memory counts after repeated LOD transitions.
  • No regression in scanning, discovery, creature events, or nearby visual quality.
