Mince Framework Audit

This audit maps the current runtime flow, where Mince is used well, where code bypasses or only partially uses it, and where systems should be split into smaller modules.

Runtime Flow​

Server boot starts in ServerScriptService/Runtime/MinceLoader.server.luau:

  1. Load replicated config from ReplicatedStorage.Runtime.Config.
  2. Load server config from ServerScriptService.Runtime.Config.
  3. Recursively require eligible modules below ServerScriptService.Runtime.Source.
  4. Register module Setup and GameStart lifecycle methods.
  5. Run Mince:Start().

Mince provides four important framework surfaces:

  • Mince:Get(name) for module lookup.
  • Mince:GetEvent(name) for remote events and named extensions.
  • Mince:GetFunction(name) for remote functions with middleware.
  • Mince:GetState(name) for server-owned replicated state.
  • Mince.Component({ Tag = "..." }) for CollectionService-tagged components.

The intended architecture is service/controller modules with explicit Setup and GameStart phases, Mince-managed remotes, Mince-managed state for replicated values, and components for tagged world instances.

High Priority Findings​

1. Profile Data Has Too Many Writers​

Many services call PlayerDataManager:GetProfileData() or GetProfile() and mutate profile tables directly. Examples:

  • StoreService edits profile.Data.Currency, profile.Data.EcoPoints, profile.Data.OwnedItems, profile.Data.Statistics, and profile.Data.GearStats.
  • PurchaseService edits PurchaseStats, PurchaseHistory, Gamepasses, and has a fallback path that directly increments currency.
  • ToolService, DefaultGearService, TipjarService, AchievementService, DiscoverySystem, TreasureService, Statistics, and Settings also mutate profile sections.

This makes persistence and replication fragile because every caller must remember to call UpdatePlayer or SchedulePlayerUpdate for the right section. It also makes validation inconsistent.

Recommended direction:

  • Keep PlayerDataManager as the persistence owner.
  • Add section-specific writer APIs instead of exposing raw profile tables for writes:
    • PlayerDataManager:Patch(player, section, patchFn)
    • PlayerDataManager:GetSection(player, section)
    • PlayerDataManager:MarkDirty(player, section)
  • Move economy writes behind CurrencyService.
  • Move inventory writes behind an InventoryService or OwnershipService.
  • Move profile stats writes behind Statistics.

2. StoreService Bypasses CurrencyService Spending​

StoreService:HandlePurchase subtracts balances directly:

  • profile.Data.EcoPoints.Balance = ecoBalance - price
  • profile.Data.Currency.Balance = balance - price

That bypasses CurrencyService:SpendCurrency, duplicated analytics logging, state sync, and future validation. It also has no matching SpendEcoPoints API.

Recommended direction:

  • Add CurrencyService:SpendEcoPoints(player, amount, source).
  • Change StoreService purchases to call CurrencyService:SpendCurrency or SpendEcoPoints.
  • Let CurrencyService own balance mutation, total spent, state sync, and analytics.
  • StoreService should only own item validation and inventory grant/equip flow.

3. PurchaseService Bypasses Mince RemoteFunction​

PurchaseService:Setup creates a raw RemoteFunction named PurchasePrompt under ReplicatedStorage.

That bypasses Mince:GetFunction, so it does not use the framework remote registry or middleware surface.

Recommended direction:

  • Replace the raw RemoteFunction with:
    • local PurchasePrompt = Mince:GetFunction("PurchasePrompt")
    • PurchasePrompt.OnInvoke = function(player, purchaseType, id) ... end
    • optional middleware for type checks and rate limits.
  • Move product/gamepass prompt validation into small methods that are easy to test.

4. Mince Lifecycle Ordering Is Only Partial​

Mince:Start() sorts SetupMethods and PostMethods, but then starts each setup with task.spawn. That means lower LoadOrder setup starts first, but it does not necessarily complete before higher-order setup starts.

Modules currently compensate by calling Mince:Get at top level or inside setup, but this can return proxy tables for modules that are not loaded yet.

Recommended direction:

  • Define lifecycle rules clearly:
    • Setup should only connect remotes/events and initialize local state.
    • GameStart should perform work that requires other modules to be ready.
  • For modules with hard dependencies, use a sequential setup group or explicit dependency metadata:
    • Dependencies = { "PlayerDataManager", "CurrencyService" }
    • Mince waits for dependency setup completion before invoking the module.
  • At minimum, document that LoadOrder controls start order, not completion order.

5. Mince Safe Require Can Hide Broken Modules​

Mince.DoPcalling = true causes require failures to become empty module tables. This keeps the server alive but shifts failures to later runtime behavior.

Recommended direction:

  • Keep pcall in production only if needed, but record failed modules in Mince.FailedModules.
  • During Studio or development, fail fast or expose a hard warning summary after load.
  • Do not register empty tables as valid modules unless the caller explicitly opts in.

6. Component Addon Depends On _G.MinceRef​

Mince/Addons/component.luau uses _G.MinceRef, and the file itself has a TODO: rewrite. This makes the component addon order-dependent and harder to isolate.

Recommended direction:

  • Pass the Mince instance into addon initialization instead of reading _G.
  • Normalize component method names: current code calls Construct, but removal code looks for Removing/Destroying; some project components use Stop, which Mince does not call directly.
  • Add a small component lifecycle adapter:
    • Construct
    • Start
    • Stop
    • Destroy

Medium Priority Findings​

1. Remote Event Extensions Are Useful But Under-Validated​

Extended events like StoreEvents:Extend("PurchaseRequest") and DrinkService:Extend("DrinkMade") help group feature traffic. The server remote addon also kicks players if they fire an unknown extension.

The current risk is that payload validation sits in each service method, if it exists at all.

Recommended direction:

  • Add optional middleware to Mince:GetEvent, similar to GetFunction.
  • Define request schemas near each remote registration:
    • Store purchase: player, category: string, itemName: string
    • Settings save: player, settings: table
    • Drink request: player, method: string, ...
  • Prefer named function remotes for request/response traffic instead of custom "Response" packets on events.

2. State Replication Is Underused​

Currency and EcoPoints now use Mince:GetState, but much of the client still receives whole profile chunks through DataSync and DataPartialSync.

Good candidates for Mince state:

  • Player economy: already partly done.
  • Settings: player-owned state with registered set handlers.
  • Inventory summary: owned/equipped state, read-only to client except through StoreService requests.
  • Gear stats: GearStats_{UserId} instead of manual GearStatsUpdate event.
  • Discovery progress: read-only state plus server request to record discoveries.

Recommended direction:

  • Use state for durable UI-facing values that change over time.
  • Use events for transient effects/notifications.
  • Use functions for request/response actions.

3. Feature Boundaries Are Blurred​

Examples:

  • StoreService owns item validation, balance spending, stats, gear stat calculation, character attributes, kit/cosmetic application, asset ownership sync, and inventory sync.
  • DrinkService owns components, recipes, cup state, ingredient rules, visuals, placement, trash logic, and client request routing.
  • TipjarService owns profile persistence, HTTP/Roblox API calls, product listing cache, rate limiting, prompts, transfers, and ledger sync.
  • ScanController owns input, camera, cursor, target selection, skeleton UI, effects, discovery events, and sound.
  • BackpackController/Main/init.luau and Utility.luau are each over 2,000 lines.

Recommended direction:

  • Split by ownership, not by folder size alone.
  • Keep public Mince module APIs small and delegate internals to private child ModuleScripts.
  • Do not let child private modules be auto-loaded by Mince; the current loader already skips ModuleScripts under ModuleScripts, which is useful for this.

Suggested Modularization​

Economy And Store​

Create or clarify:

  • CurrencyService
    • Owns Credits/EcoPoints mutation, state sync, economy analytics.
    • Exposes GiveCurrency, SpendCurrency, GiveEcoPoints, SpendEcoPoints.
  • InventoryService
    • Owns OwnedItems, grants, ownership checks, equip flags.
    • Exposes OwnsItem, GrantItem, EquipItem, UnequipItem.
  • GearStatsService
    • Calculates gear stats from equipped items.
    • Applies character attributes and speed bases.
  • StoreService
    • Owns remote request routing and store-specific validation.
    • Calls CurrencyService, InventoryService, GearStatsService, KitService.

Purchases​

Create or clarify:

  • PurchaseService
    • Owns Marketplace callbacks and receipt idempotency.
    • Uses Mince:GetFunction("PurchasePrompt").
  • EntitlementService
    • Owns gamepass lookup, player attributes, ownership sync.
  • ProductGrantService
    • Maps developer products to grant handlers.

Player Data​

Keep:

  • PlayerDataManager
    • Loads profiles, releases profiles, provides patch/dirty APIs, creates initial per-player Mince state.

Move out:

  • Section-specific mutation knowledge.
  • Economy mutation.
  • Item mutation.
  • Achievement/stat business logic.

Drink System​

Split DrinkService/init.luau:

  • DrinkService/init.luau
    • Mince module entry, remotes/functions, player cleanup.
  • DrinkService/CupComponent.luau
    • Server cup component and lifecycle.
  • DrinkService/IngredientComponent.luau
    • Ingredient rules.
  • DrinkService/DrinkDomain.luau
    • Pure recipe/mixing/name logic.
  • DrinkService/DrinkPlacement.luau
    • Placement and spawned drink handling.

Client:

  • DrinkController/init.luau
    • Setup/GameStart and high-level client state.
  • DrinkController/Input.luau
    • mouse/touch placement input.
  • DrinkController/Highlights.luau
    • ingredient/trash/drink highlights.
  • DrinkController/ClientCupState.luau
    • local state mirrored from server.

Scan Controller​

It already has submodules, but init.luau is still 1,200+ lines. Move more ownership into existing children:

  • Input should own all input bindings and device mode.
  • CursorManager should own cursor lock/sticky behavior.
  • TargetManager should own candidates/raycast/scannables.
  • EffectsManager should own depth-of-field, sounds, highlights, scanner UI effects.
  • ScanController should orchestrate state and call the Mince discovery API.

Backpack Controller​

Backpack is currently the largest client system.

Recommended split:

  • BackpackState
  • SlotModel
  • HotbarView
  • InventoryView
  • DragDrop
  • GamepadNavigation
  • VRBackpackAdapter
  • ToolBinding

Because this resembles a custom CoreGui replacement, refactor incrementally with screenshots/playtests after each slice.

Mince Usage Rules To Adopt​

  1. Top-level Mince modules return a table with Name, optional LoadOrder, Setup, and optional GameStart.
  2. Setup registers remotes, states, components, and local connections only.
  3. GameStart performs cross-module work.
  4. Use Mince:GetEvent for fire-and-forget signals.
  5. Use Mince:GetFunction for request/response flows.
  6. Use Mince:GetState for durable replicated values.
  7. Use Mince.Component for CollectionService-tagged world entities.
  8. Do not create raw remotes/functions in feature services.
  9. Do not mutate profile data outside owning services.
  10. Do not rely on _G for framework access.

Phased Refactor Plan​

Phase 1 Progress​

Completed locally:

  • PurchasePrompt now uses Mince:GetFunction("PurchasePrompt").
  • CurrencyService:SpendEcoPoints owns EcoPoint spending, state sync, and economy analytics.
  • StoreService:HandlePurchase now spends Credits and EcoPoints through CurrencyService.
  • Mince.FailedModules records require failures and reports a load summary.
  • PlayerDataManager now exposes GetSection, MarkDirty, and Patch for section-owned profile updates.
  • Settings now writes through PlayerDataManager:Patch.
  • Moonwave generation now includes StoreService and PurchaseService.

Still open:

  • Define whether Studio should fail fast on Mince.FailedModules.
  • Add typed event middleware for Mince:GetEvent.
  • Add dependency metadata or sequential setup groups for modules with hard startup dependencies.
  • Migrate remaining direct profile writers to PlayerDataManager:Patch or domain-owned services.

Phase 1: Safety And Consistency​

  • Replace PurchasePrompt raw RemoteFunction with Mince:GetFunction.
  • Add CurrencyService:SpendEcoPoints.
  • Change StoreService to spend through CurrencyService.
  • Add Mince.FailedModules and a Studio hard warning/fail mode.
  • Document LoadOrder semantics.

Phase 2: Data Ownership​

  • Add PlayerDataManager:Patch.
  • Move OwnedItems mutation into InventoryService.
  • Move GearStats calculation into GearStatsService.
  • Move discovery/settings/profile section writes behind section APIs.

Phase 3: Feature Decomposition​

  • Split StoreService and DrinkService first; they are high-value and have clear boundaries.
  • Split ScanController and BackpackController after behavior snapshots exist.
  • Move repeated UI/highlight/input logic into small reusable modules.

Phase 4: Framework Cleanup​

  • Rewrite Mince.Component to avoid _G.
  • Add event middleware.
  • Add dependency metadata or sequential setup groups.
  • Normalize component lifecycle method names.
