Runtime lifecycle

Mince is the registry and lifecycle coordinator used by both the server and client runtimes.

Boot sequence​

  1. The server loader requires ReplicatedStorage.Modules.Mince.
  2. Replicated and server configuration folders are loaded into Mince.Config.
  3. Server runtime modules are discovered recursively.
  4. Mince:Start() runs lifecycle work and establishes the server handshake.
  5. The client-context loader waits for the server setup identity.
  6. The client loads replicated configuration and replicated runtime modules.
  7. The client calls Mince:Start().

The handshake prevents client controllers from assuming the authoritative runtime exists before server startup completes.

A service module​

local ReplicatedStorage = game:GetService("ReplicatedStorage")
local Mince = require(ReplicatedStorage.Modules.Mince)

local ExampleService = {
	Name = "ExampleService",
}

function ExampleService:Setup()
	self.Remote = Mince:GetEvent("Example")
end

function ExampleService:GameStart()
	-- Begin work only after runtime setup.
end

return ExampleService

Keep module top-level code limited to dependency lookup and immutable definitions. Connections, loops, and world mutations belong in lifecycle methods so startup order remains observable.

Components​

Mince.Component { Tag = "Example" } connects behavior to CollectionService tags. A component typically implements:

MethodUse
ConstructCache instance references and initialize per-instance state
StartBegin behavior after construction
Stop or cleanup hookDisconnect listeners and release transient objects

Components are registered by instance and can be retrieved through the component registry. Parent validation prevents components from mounting in invalid hierarchies.

Discovery rules​

Mince recursively examines configured source folders, but nested ModuleScripts inside another ModuleScript act as private children. This is why Realism_Controller.Config and ScanController.TargetManager are required by their parents rather than registered as independent controllers.

Failure behavior​

The runtime's safe require path can keep startup moving after a module require failure. That is useful for availability, but it makes Studio output and targeted testing essential: a failed module can appear as an empty table until a dependent feature accesses it.

warning

Never use safe-require tolerance as validation. A clean startup must have no new require warnings, and every changed module must pass Selene and parse checks.

Adding a module​

  1. Choose the authoritative runtime band.
  2. Give the table a unique Name.
  3. Keep dependencies available on that side of the client/server boundary.
  4. Create remotes or packet schemas in replicated code.
  5. Put connections in Setup and active loops in GameStart.
  6. Make teardown explicit for components and character-bound behavior.
  7. Add the module to the module map.
